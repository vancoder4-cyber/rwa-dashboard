# RWA Dashboard Operations

## Monitoring layers

1. **Runtime resilience**
   - Upstream requests use bounded timeouts, retries, concurrency limits and CDN stale-while-revalidate caching.
   - Perp and spot venue fetches retain a last-good snapshot. A failed refresh is shown as `Stale cache`; it is never silently presented as live.
   - Missing numeric fields remain `null` and receive an explicit Full / Partial / Estimated / Unavailable status.
   - Hidden pages stop polling. When visible again, the UI recomputes and renders expiry before awaiting the next request; only stale datasets resume and concurrent refreshes for the same dataset share one in-flight request. A snapshot is actionable only while `lastSuccessAt` is valid and younger than twice the venue's normal refresh cadence.
   - Traditional ranking and quotes load only while the Traditional page is active. Rendering a hidden section must not start official-source requests.

2. **Vercel health probe**
   - `GET /api/health` first verifies that a Production deployment reports `VERCEL_GIT_COMMIT_REF=main` and a full Git SHA, then verifies the production shell, USD and FX-converted Reference Prices, the official U.S. listing directory, 24-hour Funding History sentinels for trade.xyz, Bitget, Gate, Binance and OKX, the Signal Radar Perp/Spot/OI anomaly contracts, and the freshness/exact ten-source coverage of the daily listing audit. A non-`main` Production artifact is a critical failure. The Spot anomaly check validates exact listing identity, five-source completeness, USD-volume units, OR-trigger semantics, sealed-day history, exact Perp contracts and read-only persistence state. The OI check independently validates the five exact Perp sources, strict `volume > $1m` and `peak-current > $2m` boundaries, three completed 23:00 UTC closes, same-cohort 24-hour history, public listing-sum arithmetic, Estimated field status, and the `rwa-oi-market-context/v2` price, funding and positioning contract. Funding and positioning must match the exact price representative venue/symbol. Only a representative Binance contract may carry Top Trader data; unsupported venues and missing references stay explicitly Unavailable and never borrow another venue. Warming is a warning, while Crypto leakage, invalid units/thresholds, false Full/Neutral, cross-venue context or malformed rows fail. The listing check also validates the declared retention contract and exposes `historyTruncated`; a safety-limit truncation is never a pass. The U.S. directory check requires AAPL/QQQ/BABA/TSM, validates BABA as an ADR and QQQ as an ETF, and reconciles the declared symbol/ADR/ETF counts; it never requires a ticker to remain absent forever. Legitimate securities whose tickers also exist in Crypto are permitted in the directory; those collisions and Pre-IPO identities are rejected earlier by venue/category gates. The OKX probe also checks the fixed-purpose Perp/Spot snapshots, official identity gate, reviewed listing lower bounds and mandatory ticker/OI/mark coverage.
   - Every warning/failure includes a stable remediation code, the observed reason and bounded operator actions. The endpoint remains read-only: it can recommend an authenticated Cron retry or a verified deployment promotion, but it never mutates data or aliases itself.
   - The response is `healthy`, `degraded` or `unhealthy`. A critical dashboard/reference failure, or two failed checks, returns HTTP 503.
   - Vercel Cron invokes it daily at 01:00 UTC (09:00 Asia/Shanghai). Results are visible in Function logs under `[rwa-health]`.
   - The endpoint is intentionally read-only and returns no credentials or private configuration.

3. **GitHub Actions**
   - `.github/workflows/data-health.yml` runs every day at 01:20 UTC and on demand.
   - It runs contract tests, inline-script parsing, live reference/funding/Nasdaq/OCC/OKX data contracts, the rolling seven-day competitor-listing review and the production health endpoint. Traditional checks include Top 100 cardinality, adjacent-session alignment and rank-change invariants. OKX checks keep Crypto `instCategory=1` excluded, preserve SWAP + X-Perp listings, and inner-join OI to the live catalog.
   - A failing run must be reviewed before promoting another production deployment.
   - `audit:catalog-shadow` distinguishes a Runtime Cache baseline reset from a durable lineage failure. Its remediation is read-only guidance: rebuild a fresh cache baseline with one authenticated same-bucket Cron retry, never backfill synthetic New/Re-listed events from older PostgreSQL membership, then require exact cache/database reconciliation.

4. **Codex scheduled reviews**
   - Daily at 09:10 Asia/Shanghai: production status, live data contracts, deployment state, recent errors, all ten Spot/Perpetual official catalog states and any new/re-listed assets detected in the rolling seven-day window. It also runs the production `audit:catalog-shadow` read-only reconciliation and reports consecutive healthy scheduled buckets plus the advisory three-bucket expand-shadow and seven-bucket required/read-review evidence. Phase 2 design itself has no elapsed gate, and neither advisory threshold enables a writer or read cutover.
   - Monday at 10:00 Asia/Shanghai: full venue catalogs, identity collisions, listing lifecycle, classification/tags, OKX SWAP/X-Perp and UTS/gold composition, Traditional candidate/ranking rules, previous-session selection and comparison coverage, false `NEW` detection, deterministic tie-breaks, adjusted-options handling, reference pricing and historical coverage.
   - Scheduled reviews are read-only. They report P0/P1/P2 findings and must not modify, push or deploy without user confirmation.

## Database Phase 0 / Phase 1 operations

The target model is documented in `DATABASE_ARCHITECTURE.md`; page-level inputs, formulas and current persistence are cataloged in `DATA_CATALOG_AND_FORMULAS.md`. `RWA_DATA_RULES.md` remains the identity/admission authority.

### Phase 0 — foundation only

Phase 0 provisions Neon/PostgreSQL connectivity, checksum-locked migrations, least-privilege roles, server-only feature switches, monitoring and the immutable raw-archive contract. It does **not** enable a product write or read path.

Current foundation files:

- `api/_lib/database.js` reads the server-only pooled `DATABASE_URL` lazily for runtime use. Migrations prefer `DATABASE_URL_UNPOOLED` and fall back to `DATABASE_URL` only when intentionally configured. Neither value may reach browser code, API output or logs.
- `db/migrations/*.sql` is the only schema-change path. Applied version, SHA-256 checksum and statement count are recorded in `ops.schema_migration`; an applied checksum mismatch is a hard stop.
- `scripts/migrate-db.mjs --dry-run` parses and checks migration ordering/checksums without opening a database connection. Running without `--dry-run` is an external write and requires the intended environment and explicit release authorization.

Before applying a migration:

1. confirm the target is the intended Preview/staging branch or production database; never infer this from a local `.env` file;
2. run the dry-run and database/migration unit tests;
3. confirm the migration is additive/transactional, has no default catch-all partition, and preserves stable UUID/version foreign keys rather than ticker joins;
4. apply with the migration owner, not the runtime writer;
5. verify migration ledger checksum, extensions, constraints, indexes and role allow/deny probes;
6. verify a synthetic raw artifact can be conditionally created, checksum-read and restored while secrets/headers are absent;
7. rerun the normal Preview release gate and prove all page/API payloads are byte/contract equivalent with product database writes disabled.

Minimum role boundary:

| Role | Allowed | Explicitly denied |
|---|---|---|
| Migration owner | Versioned DDL/migration ledger | Application/runtime use |
| `rwa_catalog_shadow_writer` (NOLOGIN group) | Only the explicitly granted Phase 1 identity/ingest/catalog-event tables and required sequences | DDL, market fact writes, rule changes, blanket future-table grants |
| Future fact writer | Not created or enabled in Phase 0/1 | Any connection/use until a later phase is approved |
| `rwa_analytics_reader` (NOLOGIN group) | Read-only identity/ingest/fact/analytics/publication tables | DML/DDL |
| `rwa_alert_dispatcher` (NOLOGIN group) | Read alert state; update delivery/outbox; insert delivery attempts | Identity, fact, analytics, rule or destination mutation |
| Break-glass | Not an application role; any future use must be time-bounded and audited | Routine Cron/application use |

Migration `0002` grants the migration owner membership in `rwa_catalog_shadow_writer`; the shadow transaction immediately applies `SET LOCAL ROLE` plus short statement/lock timeouts. This is the current additive bridge, not the final read-path credential model. Before any database read cutover, provision a dedicated least-privilege login and prove that the owner connection is no longer used by the application.

Safe defaults are `PG_WRITE_MODE=off` and `RAW_ARCHIVE_MODE=off`; both are server-only. `DATABASE_URL`, `DATABASE_URL_UNPOOLED` or `BLOB_READ_WRITE_TOKEN` being present never enables a writer. Phase 1 may enable only the reviewed catalog shadow path; upstream raw-body capture remains off until later collector instrumentation is separately approved.

Mode semantics are independent:

- `PG_WRITE_MODE=off|shadow|required`: off performs no PostgreSQL mutation and therefore provides no cross-instance publication lease. With PostgreSQL enabled, the writer holds a fixed 180-second database lease across the durable mutation, a post-acquire Runtime Cache re-read, cache publication and sink acknowledgement. Busy/stale/conflicting writers return 409 without mutation. A shadow-only lease service failure may preserve the Runtime Cache writer only with `publicationLease=degraded`; that cycle must fail readiness. Required-mode lease or pre-cache transaction failure prevents the Runtime Cache baseline from advancing.
- `RAW_ARCHIVE_MODE=off|shadow|required`: despite the legacy variable name, this phase controls only `normalized-catalog-v1` private-object upload. Off records a pending/skipped manifest when PostgreSQL is enabled, shadow records archive failure without blocking the current writer, and required fails before Runtime Cache advances. It never enables upstream raw-body capture.
- after the Runtime Cache write succeeds or fails, PostgreSQL mode (when enabled) records a separate `runtime-cache-listing-audit` sink result; it does not infer that outcome from database or Blob success. That post-write record is not a distributed transaction: if recording it fails after a successful cache write, the cache cannot be rolled back and reconciliation must report the missing sink evidence.

Rollback is to disable the affected switch and restore the prior application configuration. Do not delete shadow rows or rewrite migration history during rollback.

Migration and read-only verification commands:

```bash
npm run db:migrate -- --dry-run
npm run db:migrate
npm run db:migrate   # must report only [skip] on the second run
npm run audit:db
vercel env run -e production --scope vancoder4-cybers-projects -- npm run audit:catalog-shadow
```

Run migrations with `DATABASE_URL_UNPOOLED` whenever it is available. `audit:db` emits only a non-secret database fingerprint, migration checksums, role/extension results and aggregate row counts; it fails on checksum drift or privilege expansion. `audit:catalog-shadow` is read-only: it reconciles the latest bounded PostgreSQL catalog cycles with the public listing snapshot, reports consecutive healthy scheduled buckets, and returns a nonzero exit only for a reconciliation failure. Duration is operational evidence, not a market-history or product-formula gate. Never print or commit the connection URL.

### Phase 1 — ten official catalogs, shadow-write only

Phase 1 attaches an additive sink to the existing authenticated daily Listing Audit writer. Its scope is exactly the ten keys in `api/_lib/listing-audit.js`: five Perpetual catalogs (trade.xyz, Bitget, Gate, Binance, OKX) and five Spot catalogs (Bitget, Gate, Kraken, Binance, OKX).

For every UTC cycle, persist separately:

- collection cycle/attempt and one source run per expected catalog;
- deterministic `normalized-catalog-v1` artifact manifest and checksum, built from the already verified/reviewed catalog observation—not the upstream HTTP response body;
- already-admitted asset/instrument versions and per-instrument official-catalog evidence; `identity.alias_version` remains an empty schema skeleton in this phase;
- exact accepted source-run catalog membership and listing lifecycle event;
- unresolved `review-required` candidates in `identity.review_case` only; they do not create an accepted identity, instrument or membership;
- independent database/archive sink outcomes alongside the unchanged Runtime Cache result; a sink must never be inferred successful from another sink.

Within one UTC day, a trusted retry is latest-wins for that source's logical accepted membership and official-catalog evidence inside one Serializable transaction. An untrusted/Unavailable retry preserves PostgreSQL last-good membership; its current Runtime Cache diagnostic remains non-passing. Identity review resolution is recorded as identity resolution, never synthesized as a New listing. The 180-second publication lease and post-acquire cache checksum re-read prevent an older serverless invocation from overwriting a newer bundle; a missing/degraded lease can never qualify as a healthy scheduled bucket.

During Phase 1:

- `/api/listing-changes`, `/api/signal-snapshot`, `/api/health` and every page continue reading the existing Runtime Cache/CDN path;
- a database or archive error pages the shadow pipeline but does not rewrite the existing writer result or create a false production outage during the observation window;
- database success cannot hide a failed Runtime Cache writer;
- Partial/Unavailable catalogs cannot manufacture an absent/delisted membership;
- Phase 1 does not archive upstream raw response bodies and must not label `normalized-catalog-v1` as raw; `ingest.raw_artifact` is a generic manifest table whose raw-body role is reserved for a later phase;
- no price, volume, OI, funding, order-book, Top Trader, Reference, Traditional activity, aggregate, Radar anomaly or publication payload is continuously written;
- no accepted identity/instrument/membership row may admit an identity rejected, quarantined or left review-required by the existing server gate.

Phase 2 design has no elapsed-cycle gate. For operational confidence, three consecutive healthy scheduled catalog buckets are the recommendation before expanding shadow telemetry/load, and seven are the recommendation before proposing required-mode or read-cutover review. These are operator policy checkpoints, not automatic promotion: every bucket still needs all ten exact source runs and zero unexplained differences in accepted/rejected counts, identity conflicts, membership fingerprints, review-case isolation, drift quarantine, repeated-day removals and emitted lifecycle events. Replaying each `normalized-catalog-v1` artifact must reproduce the stored accepted fingerprint. Disabling either shadow sink must leave all existing APIs and UI unchanged.

#### Scheduled catalog confidence versus data-family maturity

These controls must never be reported as one:

- **Scheduled catalog confidence** counts consecutive, distinct scheduled UTC-day buckets for the ten-source official-catalog shadow writer. A same-day retry updates evidence for that bucket but does not add a bucket; a missing/non-passing scheduled bucket resets consecutive evidence. Three healthy buckets support an expand-shadow review and seven support a required/read-cutover review, but neither authorizes the change.
- **Product maturity** is formula-specific. For example, General Radar Volume/OI first scores on the 25th hourly point, Perp volume first compares on the eighth UTC date, and current Reference/Cross-Venue has no time-based warm-up.
- **Revision collection** is source-specific. Current-only catalog/ticker/reference data is appended, while funding, candles, historical OI and Traditional sessions use their own bounded overlaps. There is no universal market-history interval.

Daily Check must publish the current consecutive count, first/last qualifying UTC bucket, ten-source completeness, reconciliation differences and the reason evidence reset. It must also keep `marketFactsChecked=false` and `rollingMarketHistoryVerified=false`; catalog evidence cannot be presented as market-history verification.

#### Phase 2 prerequisites for revision-aware market history

Before any exact market-fact writer or rolling-overlap Cron is enabled:

1. migrate the event/valid-time and captured/system-time contract plus typed append-only revision relations described in `DATABASE_ARCHITECTURE.md`;
2. prove stable observation keys use source, exact `instrument_version_id`, grain/boundary, unit/currency and method version—never ticker alone;
3. expose reproducible first/latest values, `revision_count`, first-to-latest and previous-to-latest deltas without updating or deleting accepted revisions;
4. register a server-side cadence, finality lag and overlap/current-capture policy for each data family, plus a separately authenticated backfill path for older repairs; browsers cannot choose these windows;
5. version the normal/review/anomalous restatement thresholds, including zero/null handling, source precision and batch revision-rate gates;
6. test identical replay, small normal restatement, gray-zone review, anomalous drift, late completion, `value → NULL`, method/unit/identity change, old backfill and Partial/Unavailable source behavior;
7. shadow-run long enough to reconcile every revision and prove that disabling the writer leaves current Runtime Cache/CDN/API/UI behavior unchanged.

Operational clocks are data-family specific:

| Family | First usable / formula Full | Retention and Phase 2 revision policy |
|---|---|---|
| Listings | Day 1 Full baseline; Day 2 Full New/Re-listed (`0–24h`); delist `D0 present → D1 missing → D2 missing confirmed` (`24–48h` after first missing) | UI 7/30d, events 45d; append current catalogs, no historical query |
| General Radar | Point metrics first complete snapshot; Volume/OI 24 prior + current = point 25 (~24h); Full 168 total (~167h) | 168h; derived replay from versioned inputs |
| Perp volume | Seven sealed prior + current = eighth UTC date (~7d); consecutive Day 9; high-frequency Day 28; complete 30d frequency on `Day 0…37` (~37d) | 45d; rolling observations append-current with a versioned sealing rule |
| Spot anomaly | Price Day 0; volume after one prior sealed day, at the next post-midnight hourly run in the best case and within 24h; Kraken price always Unavailable | 8d retention only; rolling observations append-current |
| OI proxy | Drawdown bucket 24 (~23h); three completed 23:00 closes ~49–72h; Top Trader after alert | 96h retention; historical OI 6h hot / 48h daily / 7d weekly, otherwise append-current |
| Funding | Current immediate; >=2 settled rows and >=80% expected. Without upstream history, default 24h reaches Full at ~16h for 8h/4h cadence or ~19h for 1h; existing history can be Full immediately | Two settlements or 24h hot; 7d daily; 30d monthly; Bitget max 100 returned rows |
| Top 30 | Old history first-request Full; Day 0 fallback Estimated; new daily <=24h or trade.xyz hourly <=1h Partial | Daily 30 bars Full; trade.xyz 720h remains Estimated; daily 3–7d + T+2/monthly30d, hourly6h/daily48h |
| Traditional | Old asset rank/delta first request; new asset normally T+1; >=1 prior share/option baseline Partial | 20 sessions / four same-weekday reports (~4 weeks) Full; daily5, weekly20+4 OCC, monthly60 overlap |
| Reference | Fresh native+FX or fallback immediate | No historical maturity; current append-only, future completed close 5 sessions + T+2 |
| Cross-venue and browser-derived sections | Required fresh loaders complete = immediate | Full is source/field completeness; no independent retention/overlap |

Retention is not formula warm-up, and a formula becoming Full is not revision-validation evidence. The detailed contracts are in `DATA_CATALOG_AND_FORMULAS.md` §8.1 and `DATABASE_ARCHITECTURE.md` §4.3.1.

An identical re-fetch creates collection evidence but no revision. A changed value appends; it never silently overwrites the first value. Normal restatements remain queryable and do not page. Review-range deltas open a data-quality case. Anomalous row or batch drift is non-passing/P1, freezes promotion of that dataset and requires source-evidence review; identity/unit/method drift under the same key or destructive history mutation is P0.

### Database incident severity

- **P0**: a database migration/write changes or blocks the current production read/Cron path; identity leakage; lost immutable evidence; wrong environment migration; missing future fact partition after a later fact phase; a market-history revision is overwritten/deleted or a method/unit/identity change is accepted under the old observation key.
- **P1**: catalog reconciliation mismatch, duplicate lifecycle event, pool saturation, normalized-artifact checksum/replay failure, migration checksum mismatch, shadow sink errors over two scheduled cycles, or a future Phase 2 row/batch restatement exceeds its versioned anomalous-drift threshold.
- **P2**: non-blocking index/partition tuning, archive query ergonomics or cost optimization.

Phase 0/1 schema presence is not authorization to start market-fact ingestion or database reads. Those require a separately reviewed phase with formula conservation, replay, capacity and rollback proof.

### Database-coupled change and Preview-to-Production workflow

Every pull request must include a database-impact declaration. Use the smallest applicable class:

| Change class | Required database work in the same release |
|---|---|
| Documentation/UI only; no persisted contract changes | State `no database change`; still prove no writer/read contract changed |
| Collector, formula or contract change with an existing writer | Update the writer, immutable method/formula/cohort version, reconciliation and fixtures together; state whether existing rows remain comparable |
| Additive schema change | Add a new numbered migration, dry-run it, apply it to Preview, rerun it to prove checksum/idempotent skip, and audit roles/constraints before enabling the writer |
| Replay/backfill or retention/partition change | Add an authenticated bounded job, capacity estimate, immutable lineage and pause/resume/rollback plan; never let a browser select the repair window |
| Read cutover or destructive contract change | Use expand → dual-write/reconcile → feature-flagged read → later contract cleanup; require a separate production decision and rollback proof |

An empty skeleton does not satisfy this contract. If the changed product is not yet database-backed, document `no persisted representation yet` and leave its database writer/read switch off until the relevant phase is approved.

Release environments are paired and fail closed:

- feature/PR deployments use the isolated Preview Neon resource and Preview-only credentials;
- the production deployment uses only the Production Neon resource and Production credentials;
- database fingerprints must differ, and neither environment may fall back to the other's connection variables;
- normalized artifacts retain their environment-scoped object path; Preview evidence is never promoted or counted as Production evidence.

For a database-coupled release, execute this order:

1. Put code, migrations, formula/data registry updates, operations changes and tests in the same feature commit.
2. Run `npm test`, `npm run check:inline`, `node scripts/migrate-db.mjs --dry-run` and `git diff --check`.
3. Resolve the intended Preview database through Preview environment variables and record only its non-secret fingerprint. Abort if it matches Production.
4. Apply Preview migrations; run them a second time and require every applied migration to report a checksum-matched skip. Run `npm run audit:db`.
5. Deploy that source commit to Preview. Initialize only the explicitly enabled Preview writer, then run `audit:data`, `audit:listings`, `audit:health` and `audit:catalog-shadow` plus the browser/cache checks below.
6. Freeze the reviewed source commit and migration checksum set. Do not modify an applied migration after this point.
7. Before Production, verify the Production database fingerprint/restore policy and apply the same additive migrations with the migration owner. A migration failure stops the release before the Production rebuild or domain change.
8. Promote the reviewed Preview source or merge the reviewed commit through the configured Git workflow. Vercel performs a Production rebuild from that source using Production environment variables; do not assume Preview runtime state or credentials move with it.
9. Verify the Production source commit, database fingerprint, migration checksums, writer flags and publication-lease contract. Repeat all production audits and inspect 5xx/timeout logs.
10. Roll back the application or disable the new writer/reader flag on failure. Keep additive migrations and accepted append-only evidence; repair schema/data with a new forward migration or replay rather than rewriting the ledger.

The Daily Check database section records the deployed source commit, database fingerprint, applied migration versions/checksums, latest distinct UTC catalog bucket, ten-source and three-sink status, publication-lease state, readiness capability/operations counters and any reset reason. It must also repeat `marketFactsChecked=false` and `rollingMarketHistoryVerified=false` until a Phase 2 market-fact writer and revision reconciliation are actually enabled.

## Severity policy

- **P0**: production unavailable; RWA identity gate admits known crypto collision; widespread missing venue; materially wrong units/currency; reference or funding data could produce false trading conclusions.
- **P1**: one venue stale/unavailable; major catalog drift; historical coverage or reference source materially incomplete; Traditional comparison data mislabeled as a real rank move/`NEW`; persistent 5xx/timeouts.
- **P2**: isolated metadata/tag gaps, moderate latency, technical debt, non-blocking warnings.

## Signal snapshot operations

- Vercel Cron requests the uncached `/api/signal-snapshot-cron` route at minute 07 every UTC hour. Production must define a sensitive `CRON_SECRET`; Vercel sends it as `Authorization: Bearer …`, and the route rejects missing/mismatched credentials before source work. The public `/api/signal-snapshot` read route remains CDN cached and must never be used as the Cron target because a cache hit would skip the writer Function.
- The writer uses a stable hourly bucket, replaces the same bucket on retry, and retains at most 168 general Radar snapshots. The response and general hourly history share the same activity-ranked Top 100 canonical universe. Separately, the writer upserts one compact UTC-day bucket for every identity-verified RWA perpetual canonical asset; this daily volume history is not Top-100-limited and is keyed by `category:canonical` plus an exact sorted `venue:venueSymbol` cohort fingerprint. A third history stores eight days of exact Spot listings keyed by `spot:venue:venueSymbol`, with `category:canonical`, quote/unit and collection-method fingerprints; same-day retries replace the bucket. A fourth history stores up to 96 UTC-hourly OI observations only for exact cohorts that pass the current strict `$1m` activity filter and have complete OI; same-hour retries replace the bucket and future buckets are rejected. An asset crossing the activity threshold for the first time starts Warming instead of inheriting unmonitored low-volume history.
- The dedicated volume comparison is current rolling 24h USD contract volume divided by the mean of the preceding seven sealed UTC-date rolling-24h anchors for the unchanged cohort. These anchors are monitoring proxies, not exact UTC-calendar-day volume. Every current value, baseline, ratio and frequency conclusion is Estimated. Levels are HIGH at `ratio >= 2`, MEDIUM at `1.5 <= ratio < 2`, DOWN at `ratio <= 0.4`; two or more consecutive HIGH/MEDIUM days set consecutive expansion. Thirty-day high-frequency requires at least 21 eligible days and at least six HIGH/MEDIUM/DOWN anomaly days.
- Seven prior comparable days are required before the first ratio, so the first seven daily buckets remain Warming. A complete 30-day frequency needs 37 consecutive comparable day buckets. The compact daily history retains 45 days; a same-day Cron retry replaces that UTC-day bucket instead of incrementing history.
- The Spot board first requires current rolling-24h USD turnover of at least `$500,000`, then alerts on `current / prior sealed UTC-day anchor >= 3` OR rolling-24h gain `>= 15%`. A prior value of zero, missing prior day, changed listing/method fingerprint or non-USD unit makes the volume comparison unavailable. Price can alert on the first deployment day; Kraken price stays Unavailable because its official `o` field is UTC-day-open rather than rolling-24h-open. Bitget uses `platformTurnover24h`, never the underlying traditional-market turnover. Multiple exact quote pairs remain separate rows.
- Spot-to-Perp status is an exact identity join on `category:canonical`; the response retains all exact venue symbols/instrument types. Empty contracts means “not listed” only when all five Perp catalogs are Full. A ticker-only match, cross-category match or inferred wrapper is a P0 identity defect.
- The OI monitor first filters on aggregate rolling-24h contract volume **strictly greater than** `$1,000,000`. It emits `oi_rising` only when the same exact listing/method cohort has strictly increasing 23:00 UTC observations on the three most recent completed UTC days. It emits `liquidation_proxy` only when a gap-free same-cohort 24-hour series has `peak OI - current OI` **strictly greater than** `$2,000,000`; `both` is the OR intersection. Exact boundary values do not trigger. A changed cohort, missing hour/day, incomplete listing OI or null field stays Warming/Unavailable; a real zero OI remains zero.
- OI `rows` remains the ranked Top-100 alert view. OI `states` is the untruncated machine-consumer/recovery view and must contain one identity-unique state for every current `volumeEligibleAssets` member. `stateCoverage.complete` is true only when `expectedEligibleAssets === returnedStates === states.length`; `/api/health` fails on an omitted/duplicate state, a wrong observed UTC-hour bucket, incoherent amount/percentage arithmetic, or a false Clear claim. `triggered` and `clear` require a gap-free 24-hour same-cohort comparison; `warming` and `unavailable` carry null comparison metrics plus reason codes. Consumers must treat absence, Warming, Unavailable, or `sameCohort != true` as unknown—not recovery.
- This is a positioning/deleveraging proxy, not a trade-by-trade liquidation feed. USD OI can change with contract quantity, mark price and conversion method. A peak-to-current decline cannot identify whether longs or shorts were liquidated and must never be reported as official liquidation notional. Even at Full source/history coverage, aggregate OI, completed-day closes, 24-hour peak/drop and the resulting signal remain Estimated. Quantity-derived OI requires a positive valuation price, and mark/last or unit-method changes reset the cohort instead of creating an alert. Gate derives OI only from ticker `total_size × quanto_multiplier × positive(mark,last)`; `position_size` is long-only and a missing/invalid multiplier remains Unavailable.
- Market context uses one selected exact perpetual contract. Its 24-hour price, per-interval native funding rate and positioning identity must share the same `venue + venueSymbol`. The funding percentage is the source decimal multiplied by 100, not annualized. Binance Top Trader positioning is optional evidence only when that selected representative is Binance. The latest official one-hour row must match the exact `venueSymbol`, be non-future and no more than three hours old, have long/short percentages summing to approximately 100, and have a consistent ratio. Published ratio `>1.05` is Bullish, `<0.95` Bearish, and exact `0.95`/`1.05` Neutral. Unsupported venues, missing fields, request failures, stale timestamps or contradictory payloads are Unavailable—not Neutral—and never fall back to another venue or trigger the OI signal by themselves.
- The five source collectors are independent. A complete source outage is Unavailable; partial optional market fields remain null and downgrade the response. The Perp anomaly baseline requires all five Perp source snapshots to be Full. The Spot daily history stores volume only, so it may still be written when a Spot source is Partial solely because price-change coverage is unavailable, provided all five official catalogs are present, every admitted exact listing has volume, no catalog identity was rejected and no identity conflict exists. Any missing Spot volume, unavailable/incomplete catalog, catalog rejection or identity conflict skips that history write and makes the Cron response 503. A missing daily anchor or exact cohort-fingerprint change then fails closed at comparison time: no comparable ratio, DOWN, Normal or frequency conclusion is emitted, and a changed cohort must warm a new baseline. An incomplete current snapshot may still be displayed as Partial but must not create a false recovery/drop anomaly. If every general Perp source or every general identity-verified asset is unavailable, the endpoint returns 502 with `no-store`; an all-Spot failure is isolated to an Unavailable Spot child and is a critical `/api/health` failure rather than taking down the existing Radar payload.
- One valid, unique Binance `TRADIFI_PERPETUAL` row with a non-empty non-Crypto official type that the deployed mapper does not yet recognize is a narrow quarantine exception, not an admitted RWA. Confirm both the general and OI source objects report `catalogListingCount = listingCount + quarantinedListings`, exactly one `UNSUPPORTED_OFFICIAL_ROWS_QUARANTINED` warning, and an overall Partial/Warn response. Verified general, daily-volume and same-cohort OI histories may still write; `OPEN_INTEREST_INCOMPLETE` may coexist because individual accepted OI gaps are isolated to those assets. Two unknown rows, any malformed/duplicate symbol or base, blank/Crypto type, `IDENTITY_COVERAGE_INCOMPLETE`, catalog/upstream/source blocker, volume-wide absence, OI-wide absence or cross-category conflict must skip the affected histories and make the Cron non-200. `CN_EQUITY` is mapped to Equity and must appear as accepted `CXMT`, never as quarantine.
- Runtime Cache uses `rwa-signal-radar-v2` for the activity-ranked Top 100 hourly history, `rwa-signal-volume-daily-v1` for all-verified Perp daily anchors, `rwa-signal-spot-volume-price-history-v1` for eight days of exact Spot anchors, and `rwa-signal-oi-liquidation-hourly-v1` for 96 hours of activity-filtered, OI-complete exact cohorts. Each item is kept below 1.75 MB, below the platform 2 MB limit; capacity overflow must fail the write rather than silently drop listings. The region is pinned to `iad1` for consistent Cron/UI history.
- Runtime Cache is not the system of record. Its production status is intentionally Partial/regional best effort. An eviction or new empty regional cache must show `Baseline warming`, not `No anomalies`.
- The browser loads Radar data only on the active, visible page, promise-shares concurrent refreshes and backs off after failure. It never posts observations and never writes KPI/Radar history to localStorage.
- Review the first two Cron executions in Function logs after release. HTTP 200 is allowed only when the general-hourly, Perp-daily, Spot-daily and OI-hourly Runtime Cache writes all report `stored`; incomplete required catalog/identity coverage, a skipped write, capacity rejection or any cache failure must return HTTP 503 so the scheduler cannot record a false success (missing or invalid credentials remain 401). Confirm both hourly counts increase across distinct UTC hour buckets, repeated requests inside one hour replace rather than append both hourly buckets, and same-UTC-day retries replace rather than append either daily bucket. Confirm Perp daily coverage uses the full verified canonical universe, OI history contains exactly the current activity-eligible/OI-complete cohorts, and Spot history count equals the complete verified exact-listing universe rather than a deduplicated ticker count. General Radar point metrics may score on the first complete snapshot, but Volume/OI robust-z must remain unavailable until there are 24 strictly prior samples and the current 25th point; Full/Normal history requires 168 total points, about 167 elapsed hours. ## Competitor listing audit operations

- Vercel Cron invokes `/api/listing-audit-cron` at 00:45 UTC daily with `Authorization: Bearer $CRON_SECRET`. The public `/api/listing-changes` route is read-only and must not be used as the Cron target.
- The writer compares exactly ten independent `market:venue` catalogs and keys listings by `market:venue:venueSymbol`. Day 1's first Full pass is baseline-only and emits no New events; Day 2's Full pass can emit a verified New/Re-listed event in `0–24h`. An unavailable/invalid source retains its last-good baseline and never emits synthetic additions or removals. Delisting follows the exact live path `D0 present → D1 first complete missing → D2 complete missing confirmed`, normally `24–48h` after the first missing observation; same-day retries never advance it. Bounded pure additions pass through to reminders, while any material removal/mixed drift and extreme pure growth above both 50 listings and 50% remain quarantined for review.
- Runtime Cache namespace is `rwa-listing-audit-v2`, pinned to `iad1`, with a 45-day event-retention target, 180-day inactive-identity retention and a 1.75 MB item safety limit. V2 starts a clean baseline after expanding Gate Spot coverage to its two exact legacy commodity pairs, so that a monitoring correction is never emitted as a false New listing. State and the public snapshot are stored as one compact bundle: source catalogs reference identity keys, known identities use a compact row encoding and event history is persisted only once. The event-count safety limit may be reached before 45 days during an extreme listing burst; the API must then return `history={retentionDays,maxEvents,truncated,droppedAtLeast,droppedThrough,retainedFrom}`, prevent a Full snapshot, show retained counts as lower bounds and fail the listing audit. Truncation normally yields Partial, but a more severe source state remains Unavailable and the writer still returns 503. Runtime Cache is regional best effort, not a system of record or permanent audit database; eviction returns Warming and rebuilds baselines without turning the current catalogs into a full set of New events.
- Detection runs daily; presentation defaults to a rolling seven-day view and can switch to 30 days. Only `new` and `relisted` events appear in the board; delistings remain in server audit history. Active `pendingReviews` remain visible regardless of the selected 7/30-day window until resolved (or the source confirms removal), so an old identity question cannot disappear merely because it aged out. `Included` requires an exact same-venue `venueSymbol` match in current market data, while `review-required` remains fail closed.
- The Nasdaq Trader ETF array is a classification dependency for broad security catalogs such as Kraken xStocks: after the venue's official tokenized-asset gate, it can refine Equity to ETF. If that official ETF directory is invalid or unavailable, the affected audit source fails closed instead of guessing a category; the directory itself never proves that a product is an RWA.
- After release, inspect the first two writer runs. Day 1 Full must show Warming with zero New events; Day 2 Full may show New/Re-listed but can only mark a newly missing membership pending. A confirmed delist needs the D2 repeat-missing observation. Confirm all ten source counts are plausible, no Crypto category is admitted, Gate Spot includes only the 2026-08-14 exact live `PAXG_USDT`/`XAUT_USDT` legacy commodity exceptions plus audited wrappers, and unknown Gate-only suffix candidates remain review-required. The 7/30-day UI selector and 45-day event retention do not delay these lifecycle conclusions.
