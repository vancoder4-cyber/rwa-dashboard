# Production release rules

- Start every change from an up-to-date `origin/main`. Health-check work is not an exception.
- Never run `vercel --prod` or `vercel deploy --prod` from a local worktree. Normal Production releases come only from the Vercel Git integration on reviewed `main`. Emergency alias restoration may target only a previously verified Git-origin `main` deployment after explicit authorization.
- Do not promote a dirty, detached, stale, or non-`main` source tree. If production is wrong, first promote the last verified `main` deployment, then repair forward from current `main`.
- Before a production-capable change, run `npm ci`, `npm test`, `npm run check:inline`, `npm run verify:deploy-source` with the intended Vercel metadata, and `git diff --check`.
- After every Production deployment, `npm run audit:deployment` must independently reconcile the GitHub repository/current `main` SHA, Vercel project/source/`gitSource`/`gitDirty`, the public runtime provenance contract, and exact `index.html`/`i18n.js` hashes. A self-reported branch label or 40-character SHA is not sufficient.
- Dashboard is the sole data, identity and lifecycle authority. Its ingestion, database, release and health paths must never import, query, wait for, or mutate the Market Information Push Bot. Provenance and data contracts flow one way from Dashboard to consumers.
- Dashboard provenance/schema changes require a downstream compatibility review of `/Users/vander4/Documents/ChatGPT/市场信息推送Bot`. If the consumer is incompatible, the Bot must pause its own database/Lark mutations; it must not block, downgrade or alter Dashboard. Breaking contracts require an explicit version transition instead of silently changing an existing version.
- Treat Health Check and scheduled review code as read-only diagnostics unless a separately reviewed repair path is explicitly invoked. A diagnosis must include a stable remediation code and bounded operator actions; it must never silently mutate production data or aliases.
